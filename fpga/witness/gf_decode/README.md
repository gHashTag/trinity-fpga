# gf_decode — параметрический decode на всю GF-линейку Trinity

Sandbox design-time artifact set (2026-07-04). Синтез/PnR/прошивка на AX7203
— всегда `[ТРЕБУЕТ ДЕЙСТВИЯ ПОЛЬЗОВАТЕЛЯ]` (в песочнице нет iverilog/yosys).
Полное ТЗ: `fpga/gf16_decode_cell_TZ.md (issue #237)`.

## Зачем один параметрический модуль вместо N отдельных ядер

Единое φ-правило Trinity (проверено против SSOT `formats_catalog.t27`,
master, 2026-07-04 — держится ТОЧНО по всей лестнице из 17 GF-ячеек):

```
e = round((N-1) / φ²)
m = N - 1 - e
bias = 2^(e-1) - 1
```

Поскольку decode-закон (5 классов: normal / subnormal / zero / Inf / NaN)
одинаков для ЛЮБОГО (E, M, BIAS), один Verilog-генератор
`gf_decode_param.v #(N, E, M, BIAS)` покрывает всю Фазу A (10 форматов) —
вместо переписывания отдельного decode-ядра под каждый формат. Это ключевой
аргумент для рецензента ARITH в обеих статьях
([arXiv:2606.05017](https://arxiv.org/abs/2606.05017),
[arXiv:2606.09686](https://arxiv.org/abs/2606.09686)).

**gf16 (issue #237)** — не отдельная сущность: это просто инстанс
`#(N=16, E=6, M=9, BIAS=31)` этого же генератора. Issue #237 закрывается как
частный случай, отдельное ядро для gf16 не нужно.

## Фазировка (по decode_target из SSOT)

### Фаза A — FP32-линейка (10 форматов) — 10/10 PASS на iverilog-witness №2 (после ДВУХ фиксов)

`gf4, gf6, gf8, gf10, gf12, gf14, gf16, gf20, gf24, gf32` → выход IEEE
binary32. **10/10 Phase-A PASS подтверждено настоящим independent
iverilog-witness №2** (fixed-width семантика реального симулятора), НЕ только
Python-моделью. Golden Fraction-оракул == Python бит-модель == iverilog-RTL.

**Путь к зелёному потребовал ДВУХ fixed-width фиксов, которых Python-модель
НЕ видела** (урок 04.07, подтверждает урок 28.06):

1. **Fix #1 (widen-before-shift, баг #4 ниже)** — чинит gf16-class (форматы
   вне FP32-subnormal packer). Первый прогон v1 RTL: gf16 exhaustive
   `HW RESULT: 1168/65536 bit-exact (fails=64368)` — ~98% провал из-за
   обрезки сдвига в M-битном контейнере.
2. **Fix #2 (widen sub_shifted [M:0]→[23:0], баг #5 ниже)** — widen-фикса
   НЕ достаточно: gf24/gf32 всё ещё падали (`dut=00Xxxxxx`) из-за
   out-of-bounds чтения `sub_shifted[22:0]` из `[M:0]`-провода (для gf24
   M=14 → биты 22:15 OOB → X). Срабатывает ТОЛЬКО при true_exp < −126
   (deep underflow → FP32-subnormal path), куда gf16 (BIAS=31) не попадает —
   поэтому gf16 был чист и скрывал баг. Python-модель не имеет понятия
   OOB-read → снова не поймала.

Оба фикса применены в `gf_decode_param.v` (sandbox-версия синхронизирована с
верифицированным-зелёным RTL пользователя). Верифицированный RTL + witness-
harness (`gen_golden.py`, `gen_tb.py`, TBs, iverilog-логи) — в
`/tmp/gf16_witness/` у пользователя. **Статус: [verified SW] на iverilog**
(fixed-width sim, НЕ HW-синтез/прошивка). decode-HW галочка (4/4 цепь на
AX7203) остаётся `[ТРЕБУЕТ ДЕЙСТВИЯ ПОЛЬЗОВАТЕЛЯ]`.

### Фаза B — FP64-линейка (gf48, gf64) — СЛЕДУЮЩИЙ ШАГ

Тот же generator, выход IEEE binary64 (11 бит эксп / 52 бита мантисса).
`gf_decode_ref.py` уже содержит `gf_decode_to_fp64_bits()` и параметры
gf48 (E=18,M=29,BIAS=131071) / gf64 (E=24,M=39,BIAS=8388607) в каталоге
`GF_LINEUP`, но Verilog-модуль для binary64-выхода, бит-модель и вектора для
Фазы B в этом лупе НЕ производились — это `[СЛЕД. ЛУП]`. Мантисса обоих
форматов (29 и 39 бит) помещается в 52-битную мантиссу binary64 без потерь,
поэтому подход (LZC-нормализация субнормалей, rebias BIAS→1023) переносится
без принципиальных изменений.

### Фаза C — extended (gf96…gf1024) — SW-only, НЕ обещать FP-decode на HW

Мантисса (59…632 бита) не влезает даже в binary64 (52 бита). Для этих 5
форматов `gf_decode_ref.py` даёт только точный SW-эталон (`decode()` на
`Fraction` работает для ЛЮБОЙ ширины — это уже реализовано и проверено
φ-правилом). Аппаратный FP-decode на HW для extended = **[открытая гипотеза
для HW]**, никогда не заявлять как реализованный. При появлении реальной
потребности — fixed-point или chunked-limb (double-double-style) decode,
НЕ единый FP32/FP64 путь.

## Результаты сверки golden == RTL (без железа)

Методология — по образцу денормал-лупа
(`(методология денормал-лупа, вне репо)` §4): (1)
golden на точной арифметике, (2) бит-модель RTL с масками ширины полей на
каждом присваивании (урок 28.06 про fixed-width баги учтён), (3) exhaustive
для малых форматов, representative + 5 обязательных классов для крупных.

| Формат | N | BIAS | Покрытие | Проб | Fails | Вердикт |
|---|---|---|---|---|---|---|
| gf4  | 4  | 0    | exhaustive      | 16/16     | 0 | **PASS** |
| gf6  | 6  | 1    | exhaustive      | 64/64     | 0 | **PASS** |
| gf8  | 8  | 3    | exhaustive      | 256/256   | 0 | **PASS** |
| gf10 | 10 | 3    | exhaustive      | 1024/1024 | 0 | **PASS** |
| gf12 | 12 | 7    | exhaustive      | 4096/4096 | 0 | **PASS** |
| gf14 | 14 | 15   | representative+5cls | 4122/16384 | 0 | **PASS** |
| gf16 | 16 | 31   | representative+5cls | 4122/65536 | 0 | **PASS** |
| gf20 | 20 | 63   | representative+5cls | 4040/1048576 | 0 | **PASS** |
| gf24 | 24 | 255  | representative+5cls (+ full-exponent stress) | 4038 + 9198 | 0 | **PASS** |
| gf32 | 32 | 2047 | representative+5cls (+ full-exponent stress) | 4038 + 73710 | 0 | **PASS** |

**Итог: 10/10 Фазы A PASS golden==RTL [смоделировано].** Запуск:
`python3 rtl_bit_model.py` (exit code 0 = все PASS).

GF4 (bias=0, e1m2) — вырожденный край проверен ОТДЕЛЬНО: EXP_MAX=1 целиком
занят Inf/NaN, нормального диапазона у GF4 нет (только subnormal/zero/Inf/
NaN — экспериментально подтверждено: классы, встречающиеся в 16/16 кодов =
`{inf, nan, subnormal, zero}`, `normal` отсутствует, что ожидаемо). Общий
параметрический decode корректно обрабатывает этот край БЕЗ отдельного ядра
(в отличие от GF-ADD денормал-фикса, где арифметика на bias=0 требовала
отдельного ядра — decode не делает выравнивание экспонент между операндами,
поэтому вырожденность GF4 не создаёт для него отдельной проблемы).

### Найденные и исправленные баги (в процессе этого лупа)

1. **Знак нуля терялся в golden-оракуле.** `decode()` изначально всегда
   возвращал `Fraction(0)` без знака для `exp=0,mant=0`, тогда как RTL
   корректно сохраняет знак (`-0`). Фикс: класс `SignedZero(Fraction)` с
   атрибутом `.sign`, используемый при конверсии в IEEE-биты. Без этого
   фикса ложно репортились расхождения на КАЖДОМ формате (1 fail на
   формат, код `raw = 1<<(N-1)`, т.е. отрицательный ноль).

2. **Критичный баг decode-ЗАКОНА (не транскрипции): underflow-to-zero
   вместо gradual underflow в FP32.** Для форматов с `BIAS_gf > 127`
   (gf24 BIAS=255, gf32 BIAS=2047) часть GF-нормального диапазона имеет
   истинный экспонент ниже минимального нормального экспонента FP32
   (-126), но всё ещё представим как FP32-**субнормаль**. Первая версия
   алгоритма (и в бит-модели, и в Verilog v1) при `rebias-exp <= 0` просто
   флешила результат в 0 — потеряно 187/4038 (gf24) и 22/4038 (gf32)
   значений в representative-выборке. Найдено сравнением с golden
   (`fraction_to_ieee754_binary32_bits`, которая сама умеет насыщать
   правильно через нативный float). Исправлено: единая функция `_pack_fp32`
   (Python) / общий packer-датапат (Verilog v2), которая всегда пытается
   FP32-normal путь, а при `true_exp < -126` переключается на
   FP32-subnormal путь с явным guard/round/sticky относительно
   FP32-субнормальной LSB (2^-149).

3. **Промежуточная ошибка при первой попытке фикса #2**: guard/sticky
   считались относительно `FP32_MIN_NORM_EXP=-126` вместо правильной
   опорной точки `FP32_SUB_LSB_EXP=-149` — это давало `shift` за пределами
   значащих бит и ошибочно округляло все такие значения В НОЛЬ вместо
   ближайшего представимого субнормала. Контрпример: `gf24 raw=0x1a4d56`,
   точное значение `0.604 × 2⁻¹⁴⁹`, обязано округлиться в **1** (младший
   FP32-субнормал), а не в 0. Исправлено формулой
   `shift = frac_w - true_exp + FP32_SUB_LSB_EXP`. После фикса —
   0 расхождений на полном стресс-тесте по всем степеням экспоненты gf24/
   gf32 (9198 и 73710 проб соответственно).

Ни одного расхождения, отнесённого к sticky-биту при ВЫЧИТАНИИ (та
проблема специфична для GF-ADD, decode не делает вычитание операндов) или
к implicit-биту денормалей (implicit=0 для subnormal обрабатывался верно с
самого начала в обеих реализациях).

4. **Fixed-width shift truncation в Verilog (поймано ТОЛЬКО iverilog, не
   Python) — урок 28.06 в действии.** Строка 180 (v1) `gf_decode_param.v`:
   `assign norm_widen_result = { {(WIDE-FP32_MANT+1){1'b0}}, (pack_frac <<
   (FP32_MANT-M)) };`. `pack_frac` объявлен `[M-1:0]` (M бит), а в Verilog
   ширина результата сдвига равна ширине ЛЕВОГО операнда — то есть
   `pack_frac << (23-M)` вычислялся в M-битном контейнере и старшие
   значащие биты, ушедшие за границу M, **обрезались ДО** конкатенации.
   Python-бит-модель (`frac_bits << shift_amt` в arbitrary-width int, потом
   `& mask(23)`) моделировала МАТЕМАТИЧЕСКИ правильную (целевую) семантику,
   поэтому давала PASS и НЕ видела обрезку. Симптом на реальном
   Verilog-симуляторе: gf16 exhaustive `HW RESULT: 1168/65536 bit-exact
   (fails=64368)` — падало ~98% нормалей (тем сильнее, чем меньше M и больше
   сдвиг). **Фикс (v2):** сначала расширить до полной ширины результата,
   потом сдвигать —
   `wire [WIDE:0] pf_wide = { {(WIDE-M+1){1'b0}}, pack_frac };`
   `assign norm_widen_result = pf_wide << (FP32_MANT - M);`. Арифметика фикса:
   для всех 10 форматов сдвиг `= (23-M) >= 0`, значащих бит после сдвига
   `= M + (23-M) = 23 <= WIDE=23`, плюс бит carry `[23]` = 24-битный контейнер
   `[WIDE:0]` вмещает без потерь; carry на widen-пути = 0 (нормальная
   мантисса ≤23 бит). Фикс чинит gf16-class; НО одного его НЕДОСТАТОЧНО —
   см. баг #5.

5. **Out-of-bounds bit-read в FP32-subnormal packer (поймано ТОЛЬКО iverilog №2).**
   После fix #1 gf16 стал чист, но gf24/gf32 продолжали падать с выходом
   `dut=00Xxxxxx`. Корень: `wire [M:0] sub_shifted` (для gf24 M=14 → 15 бит),
   а ниже читается `sub_shifted[22:0]` → биты 22:(M+1) = out-of-bounds → X.
   Срабатывает ТОЛЬКО на FP32-subnormal пути (true_exp < −126, deep
   underflow), куда gf16 (BIAS=31) никогда не попадает, — поэтому gf16
   оставался чистым и скрывал этот баг (вот почему fix #1 выглядел
   достаточным на gf16). Python-бит-модель не имеет понятия OOB-read
   (arbitrary-width int не бывает «шире объявления») → снова PASS без
   предупреждения. **Фикс:** `wire [M:0] sub_shifted` → `wire [23:0]
   sub_shifted` (RHS zero-extends до 24 бит, `[22:0]` читает валидные
   нули). После обоих фиксов — **10/10 Phase-A PASS на iverilog** (fails=0).

## Honesty-статус (binding)

- φ-правило = **[Verified как правило]** — держится точно по всей 17-ячеечной
  лестнице (проверено `gf_decode_ref.py::verify_phi_rule()`).
- golden==Python-бит-модель = **[смоделировано]** (спецификация); сама по себе
  НЕ гарантия Verilog-RTL (баги #4 и #5: модель прошла, Verilog падал до
  ДВУХ фиксов).
- Verilog `gf_decode_param.v` (оба фикса) = **[verified SW на iverilog-witness
  №2]** — 10/10 Phase-A `HW RESULT: N/N bit-exact (fails=0)` на реальном
  симуляторе с fixed-width семантикой. Это sim-bitexact, НЕ HW: decode-HW
  требует 4/4 цепи на AX7203 (synth+flash+UART+IDCODE), которая НЕ выполнена.
- gf16-decode из этого generator закрывает **#237** как частный случай.
- 1-ULP subnormal residuals — не встречены в проведённых прогонах для
  Фазы A (0 расхождений на всех классах); если появятся на реальном железе,
  это будет `KNOWN_LIMITATION`, не hard-fail (см. gf_decode_lineup_spec.md).
- extended (gf96…gf1024) — SW-conformance / fixed-point ТОЛЬКО, никогда не
  заявлять FP-decode на HW.
- Каталог = 83 формата (эта работа = 17-ячеечное GF-подсемейство внутри
  каталога). Никаких «первый/лучший».
- Каждый формат остаётся decode-HW **[требует подтверждения]** до полной 4/4
  цепи (CI GREEN + SHA256 + UART `HW RESULT: N/N bit-exact (fails=0)`
  @160000 + IDCODE `0x13636093`) на AX7203 — см. критерии Tier-E в
  gf_decode_lineup_spec.md.

## Что осталось за пользователем (вне песочницы)

1. **iverilog-witness №2 — ГОТОВО (зелёный, оба фикса).** 10/10 Phase-A
   `HW RESULT: N/N bit-exact (fails=0)` на реальном iverilog у пользователя
   (harness + логи в `/tmp/gf16_witness/`). Опционально (вариант 3): более
   сильный witness — exhaustive gf20 (2^20=1M) / gf24 (2^24=16M) вместо
   representative-выборки (долго, но возможно).
2. **Синтез + PnR + прошивка на AX7203** (XC7A200T-2FBG484I,
   IDCODE `0x13636093`) для каждого из 10 форматов Фазы A — только тогда
   можно закрыть decode-HW галочку (4/4 цепь).
3. **CI-workflow(ы)** synth→битстрим по образцу corona-decode-* — один
   параметрический workflow с `strategy: matrix:` по 10 строкам (N/E/M/BIAS)
   либо 10 отдельных workflow-файлов, по аналогии с существующими
   `gf6_add`/`gf8_add`/... в trinity-fpga.
4. **Расширение FMT-списка corona-decode-host** на всю GF-линейку + fmt-коды
   (аналогично существующим 13 decode-HW форматам, см. wave-loop skill
   §«decode-HW 13 (Тир E)»).
5. **Фаза B (FP64: gf48/gf64)** — Verilog-модуль с binary64-выходом,
   бит-модель, вектора — по аналогии с этим лупом, но с 11-битной эксп./
   52-битной мантиссой FP64.
6. **Фаза C (extended)** — решение о fixed-point/chunked-limb SW-conformance
   подходе (НЕ FP-decode) для gf96…gf1024.
7. Публикация UART-логов на issue #199 (эпик fpga-matrix) после каждой
   успешной 4/4 цепи, по шаблону из `burst-flash-checklist.md`.
