# Perplexity for the 16-bit-class tie trio: nobody wins — 2026-08-19

The T54 accuracy tie (`conformance/tekum_true_bench.py`, recorded in
`research/TEKUM_VS_TNF_LINE_2026-08-19.md` §2) stands on NRMSE accumulation:
16-bit class tekum10 8.56e-3 / takum16 5.70e-3 / TNF(4,8) 5.32e-3. The block
axis showed perplexity can reorder NRMSE rankings
(`research/block/BLOCK_AXIS_VERDICT_2026-08-10.md`), so the tie had to be
checked on a live model. It was, on the block verdict's own pipeline.

**Verdict, plainly: no format wins.** Elementwise scalar quantisation at the
16-bit class is invisible to this pipeline — every measured row sits within
0.0009 ppl (0.006%) of the FP32 baseline, several rows land *below* it, and
the ordering flips between quantisation scopes. The T54 tie survives on a
live model in the strongest possible form: not "still a tie by a small
margin" but "the end-task metric cannot separate the three formats from each
other, or from FP32."

## Setup

* Script: `conformance/ppl_16bit_trio.py` (this measurement's instrument).
* Pipeline: identical to `research/block/block_tnf.py` — SmolLM2-135M,
  wikitext-2 test, 40 windows of 2048 tokens, the same `loss*(SEQLEN-1)`
  accumulation and the same ruler check. **The FP32 baseline reproduced the
  2026-08-10 verdict's ruler exactly: 14.4874.** The pipelines are the same
  by measurement, not by claim.
* Quantisation: elementwise, scalar, NO block scale. Per-tensor `s = amax(|W|)`
  pre-scales each tensor so its largest magnitude lands exactly on 1.0 — a
  code in all three formats, so the top is never clamped; every element goes
  value → nearest code → decoded value; the same `s` inverts the scaling.
  One rule, identical for all three formats.
* Oracles: `conformance/tnf_ref.py` (TRUE_LADDER rungs TNF(4,8)/TNF(4,24)),
  `conformance/takum_ref.py` (linear takum model, post-#606),
  `conformance/tekum_true_ref.py` (true base-3, widths in trits).
* Fast paths: 16-bit class snaps against the fully enumerated signed
  codebooks (40,449 / 65,535 / 33,307-in-range codes) by midpoint bucketize —
  exact nearest-code by construction; 32-bit class rounds per binade/triade
  with neighbour-bucket candidates. All seven validation gates against the
  Fraction oracles passed with **0 mismatches in 1000 seeded random values
  each** (seed 19), including the exact code-level check for tekum20, before
  any weight was touched.
* Determinism: no randomness in the measurement path; model
  `HuggingFaceTB/SmolLM2-135M` snapshot
  `93efa2f097d58c2a74874c7e644dbc9b0cee75a2`; dataset
  `Salesforce/wikitext` snapshot
  `b08601e04326c79dfdd32d625aee71d232d685c3`, file
  `wikitext-2-raw-v1/test-00000-of-00001.parquet`; torch 2.11.0,
  numpy 2.4.3, CPU float32, offline HF cache.

Two scopes, both reported: **every-tensor** (all 272 storage-deduped
parameter tensors — embeddings, norms, biases; the tied lm_head follows the
embedding) and **linear-only** (all 210 `nn.Linear` except lm_head — the
block-axis verdict's exact target set).

## Reading the 16-bit rows honestly

* **The spread is below the metric's resolution.** Largest deviation from
  baseline in either direction: 0.0007 ppl (linear-only TNF(4,8), and it is
  a deviation *downward* — quantisation "improving" perplexity). The
  between-scope difference for the same format (TNF: 14.4876 vs 14.4867)
  exceeds every between-format difference within a scope. Ordering by these
  digits would be ordering noise: in every-tensor scope TNF is nominally
  last; in linear-only it is nominally first. Both readings are meaningless
  at this magnitude, and we decline both.
* **Perplexity did not reorder the tie into a win — it erased the contrast
  entirely.** The block axis reordered rankings because 4–6-bit formats do
  real damage (ppl 14.7→36.7). At the 16-bit class the weight NRMSE is
  ~1e-3–1e-4: three orders below the level where this pipeline registered
  anything on the block axis.
* **The one real separation is in weight NRMSE, and it ranks TNF last.** On
  amax-pre-scaled weights: tekum10 2.19e-04 < takum16 3.22e-04 < TNF(4,8)
  8.21e-04 — a 3.7× spread, *reversed* from T54's accumulation ranking
  (where TNF(4,8) 5.32e-3 was best and tekum10 8.56e-3 worst). The mechanism
  is the taper: pre-scaling puts the weight mass within a few binades of
  1.0, inside the region where takum/tekum still carry 9–11 fractional
  bits-equivalent, while TNF(4,8) spends a flat 8-bit mantissa
  everywhere. T54 measured accumulation across ±3 decades, where the flat
  mantissa is the better bargain; near the taper's centre it is the worse
  one. Both measurements stand; they measure different regimes. Neither
  reaches perplexity at this width — and tekum10 posts its NRMSE win while
  storing 0.15 fewer bits than the other two, which is worth saying out
  loud since the direction is against us.

## Consequence for the line

The 16-bit-class element-axis conclusion of
`research/TEKUM_VS_TNF_LINE_2026-08-19.md` — a three-way tie, no format wins
more than the width it gives up — **survives contact with a live model**,
and gets a sharper form: at this width the choice among TNF(4,8) / takum16 /
tekum10 is invisible to SmolLM2-135M wikitext-2 perplexity. Nothing here
feeds the publication stop-rule either way: the stop-rule's axis is the
block axis, where the verdict against us stands unchanged. On the element
axis the differentiator between these formats is not accuracy at 16 bits —
it is hardware cost (§3 of the line doc), where the asymmetry is 38×.

## Caveats

* One model (SmolLM2-135M), one dataset (wikitext-2 test), 40 windows,
  weights only, post-training rounding — no activation quantisation, no
  finetuning. A claim about this pipeline, not about all models.
* Quantised values are cast back to float32 model weights; base-3 values are
  not float32-exact. The reconstruction error is bounded by float32's own
  2^-24 relative step, identical treatment for all formats, and is the same
  cast the block-axis pipeline used.
* `takum_ref.py` is the linear structural model of takum's field layout, not
  the logarithmic original — the same instrument and caveat as T54.
* The tekum specials ambiguity (`tekum_true_ref.py` header) affects two
  codes per width, both outside the pre-scaled range; it cannot touch these
  numbers.
* Deltas at the 4th decimal of ppl are reported as measured but explicitly
  not interpreted; the scope-flip above is the evidence they are noise.
