# BENCH-007: прогон своими руками

<!-- doc-refs: names-absent-files-by-design -->
<!-- Раздел 0 называет исходники обучалки, которых ещё нет в публичных репо; разделы 3–4 — файлы, которые появятся после замера (MEASURED.md, results/). -->

**Цель.** Одна сессия на плате даёт три измеренных числа с сырыми данными:
1. рабочая частота на кристалле, измеренная против кварца, а не взятая из настроек;
2. скорость, шагов в секунду;
3. мощность платы в простое и под нагрузкой.

Из них получается энергия на шаг или честная верхняя граница.

Всё, что ниже помечено **[сейчас]**, делается без чужих файлов. Помеченное **[после обучалки]** ждёт исходников обучалки XOR, которых пока нет в публичных репо.

## 1. Что должно лежать на столе

| что | зачем | проверка |
|---|---|---|
| AX7203 + родной БП 12 В | — | горит индикатор питания |
| JTAG-кабель AL321 (FT232H, «Digilent USB Device», 10-pin) | без него не прошить | `openFPGALoader --detect -c digilent_hs2` → `idcode 0x3636093`, `artix a7 200t` |
| mini-USB в порт CP2102 на плате | UART | появится `/dev/cu.SLAB_USBtoUART` или `/dev/cu.usbserial-…` |
| **Измеритель мощности с записью в файл** на входе 12 В | мощность | см. ниже |
| Mac: `brew install openfpgaloader`, `pip3 install pyserial` | прошивка и захват | `openFPGALoader --help` |

**Измеритель.** Нужны запись в файл и разрешение хотя бы 1 мВт. Варианты по убыванию удобства:
- **FNIRSI FNB58 + кабель USB-C PD → 12 В на штекер платы + зарядка, у которой есть профиль 12 В PD.** Многие зарядки дают только 9/15/20 В: смотри PDO в самом FNB58 до подключения платы. Лог на Mac: [fnirsi-usb-power-data-logger](https://github.com/baryluk/fnirsi-usb-power-data-logger) (`pip3 install pyusb crc`, `brew install libusb`; автор тестировал только Linux). Его вывод `b7_analyze.py` читает как есть.
- Лабораторный БП с логированием через USB (например, Riden RD6006 и аналоги).
- Встраиваемый DC-ваттметр только с экраном. Тогда видео экрана и ручная выписка раз в секунду. Это самый слабый вариант, но лучше, чем ничего.

Диаметр штекера сверь с родным адаптером платы до покупки кабеля.

**Битстрим пробы уже собран:** `bench007_probe_ax7203.bit`, sha256 `9a4e5c2bccbeca3c…` (полный — в `.sha256`).
- Собран в GitHub Actions этим воркфлоу (run 35993961960, seed 1), образ openXC7 закреплён по digest; подробности в `build_log/provenance.txt`. Конфигурационные данные совпадают байт в байт с двумя другими сборками тех же исходников, отличается только заголовок (путь и время).
- Все три клока ограничены в XDC. Timing выполнен без `--timing-allow-fail`: ref_clk 189,18 МГц при цели 100, dut_clk 176,80 МГц при цели 100 (реально ~70), clk200 1221 МГц при цели 200.
- Логи yosys и nextpnr лежат в `build_log/`.
- **На железе не проверялся:** первая загрузка и есть проверка.

Пересобрать самому: Actions → «BENCH-007 probe (AX7203)» → Run workflow (воркфлоу `.github/workflows/bench007-probe-ax7203.yml`, образ закреплён по digest).

## 2. Сессия A [сейчас]: частота кристалла и проверка всей цепочки

Проба `bench007_probe_ax7203` меряет **CFGMCLK** — внутренний генератор. На нём работают все JTAG-дизайны в t27 (`gft_train1`, классификатор). В репо записан разброс 68,8–70,77 МГц по трём кристаллам, эта сессия даст число именно для твоего. Заодно проверяется вся цепочка «битстрим → прошивка → захват → расчёт → отчёт» до того, как на плате окажется настоящая нагрузка.

1. Питание через измеритель. Подключить JTAG и UART. **10 минут прогрева.**
2. `openFPGALoader --detect -c digilent_hs2` — должен быть IDCODE `0x3636093`.
3. `shasum -a 256 bench007_probe_ax7203.bit` — сверить с `.sha256` рядом.
4. `openFPGALoader -c digilent_hs2 bench007_probe_ax7203.bit` — ждать `done 1`. Это загрузка в SRAM: после выключения питания исчезнет, прошивку во флеше не трогает.
5. Светодиоды (номера `led[n]` — порты `rtl/bench007_probe_ax7203.v`, пины в `.xdc`):
   - `led[0]` (B13) мигает ~0,75 Гц — путь 200 МГц от кварца жив;
   - `led[1]` (C13) ~0,5 Гц — CFGMCLK жив;
   - `led[2]` (D14) вспыхивает раз в секунду примерно на 3 мс — идёт строка отчёта.

   Если `led[1]` мигает, а `led[0]` нет и в UART тишина, умер путь 200 МГц. Дальше не идти.
6. `python3 host/b7_capture.py --tag probe --seconds 300`. Пять минут, чтобы увидеть температурный дрейф.
7. `python3 host/b7_analyze.py --uart "raw/uart_probe_*.log" --expect-step-div 1024 --out results/probe`

**Чего ждать.** Около 69–71 МГц, самопроверка инструмента **PASS**, 0 битых строк. Если самопроверка FAIL, сломан инструмент, а не плата: числа не использовать, скрипт выйдет с ошибкой.

Параллельно с шагом 6 пиши мощность: это базовая линия «плата + проба».

## 3. Сессия B [после обучалки]: обучалка XOR — скорость и энергия на шаг

**Определения, фиксируются заранее:**
- **idle** — битстрим загружен, драйвер не запущен (ядро ждёт `start`, клок идёт);
- **active** — `drive_bpseq.py` непрерывно гоняет эпохи;
- **шаг** — один образец: forward + backprop + обновление весов.

1. Проверить sha256 битстрима против закоммиченного, прошить.
2. Контрольный прогон: `python3 -u drive_bpseq.py /dev/cu.usbserial-… | python3 host/b7_capture.py --stdin --tag xor_check --seconds 600`. Флаг `-u` обязателен: без него вывод буферизуется и все строки получат одну метку времени, скорость будет мусором. Нужно XOR 4/4 и траекторию весов как у модели. Если не 4/4, дальше не идти: на этом сиде плата считает неверно (seed-лотерея, см. методологию).
3. Мощность: **ABABAB** — idle 90 с, active 90 с, по три раза, **чередуя**, а не AAABBB, чтобы дрейф не лёг в разницу. Между повторами кабели не трогать, температуру в комнате записать.
4. Каждый active-повтор писать через `b7_capture.py --stdin --tag xor_active_rN`.
5. Расчёт:

```
python3 host/b7_analyze.py \
  --host-steps "raw/uart_xor_active_r*.log" --step-regex '<строка драйвера на один шаг>' \
  --step-name "training step" \
  --power "idle=raw/p_idle_r1.csv,raw/p_idle_r2.csv,raw/p_idle_r3.csv" \
  --power "active=raw/p_active_r1.csv,raw/p_active_r2.csv,raw/p_active_r3.csv" \
  --meter "FNIRSI FNB58" --meter-res-w 0.001 --meter-acc-pct 0.5 \
  --out results/xor
```

**Частота обучалки** берётся из её RTL и XDC, когда они будут в репо. Если ядро работает от 200 МГц кварца с clock-enable, частота равна кварцу ±50 ppm, а сессия A подтверждает, что этот путь жив. Если там свой внутренний клок, в дизайн обучалки нужно вставить `rtl/bench_meter.v`: вход `dut_clk` — клок ядра, `dut_step` — импульс «шаг готов», TX на свободный пин + USB-UART за $3, потому что штатный UART занят драйвером.

**Чего ждать от мощности.** Ядро около 3K LUT на 200T-кристалле, плата целиком с DDR3 — несколько ватт. Разница active−idle может оказаться десятками милливатт или меньше разрешения прибора. Тогда скрипт напишет **NOT resolved** и выдаст верхнюю границу. Это нормальный, публикуемый результат. Подгонять не надо.

## 5. Готово, когда

- [ ] Сессия A: частота CFGMCLK измерена, самопроверка PASS, сырые логи с sha256 в репо.
- [ ] Битстрим пробы собран с выполненным timing: лог nextpnr лежит рядом с `.bit`, `--timing-allow-fail` не использовался.
- [ ] Сессия B: sha256 битстрима обучалки совпадает с закоммиченным, XOR 4/4 на плате, лог в репо.
- [ ] Сборка обучалки: либо timing выполнен, либо прямо написано, что был `--timing-allow-fail`, и указан seed.
- [ ] Мощность: 3×idle + 3×active чередованием; модель прибора, разрешение и точность записаны; CSV в репо.
- [ ] ΔP: значение или верхняя граница; энергия на шаг — из скрипта.
- [ ] Видео одним куском.
- [ ] В `MEASURED.md` есть раздел «чего этот замер не показывает».

## 6. Чего не писать после замера

- Частоту комбинационного блока: у него нет регистров, значит нет и частоты. Именно так отозвали 323 МГц.
- «Кремний» про FPGA. Кристалла ASIC не было.
- Экстраполяцию на ASIC или «в N раз эффективнее GPU» из этого замера.
- tok/s: полной модели на ядре нет.
- «Энергию на инференс»: меряется шаг обучения сети 2-2-1 в GF-T на Artix-7.
